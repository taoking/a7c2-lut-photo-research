# LUT 链路调查：上下文句柄输出与释放边界

日期：2026-10-19。本轮跨日接续[第十二轮](LUT链路调查记录-第十二轮.md)，继续只读已有官方原版 CP 2.01；材料指纹见[交接](HANDOFF.md)。本轮完成离线调查、工具与验证，没有操作相机或生成机内载荷/补丁。

本轮将 LUT 上下文 `+0x13b4` 的一处输出指针连到任务记录和服务返回字段，并确认捕获模块的另一类打开、引用计数释放与注册表类型字清除。**服务层令牌与捕获驱动句柄是否相同、照片 LUT 使能、有效像素地址和 MAIN 缓冲仍未证实；机内直出和总任务未完成。**

## 1. LUT 上下文字段的输出指针已找到

在 `0x3b9b02`，程序把当前上下文 `+0x13b4` 的地址放入调用栈 `+0x18`，随后调用 `0xa28e92`。向下的指针传递如下：

| 被调函数 | 指针位于入口 SP 的偏移 | 下传时位于当前 SP 的偏移 |
| --- | --- | --- |
| `0xa28e92` | `+0x18`，以 `r7+0x20` 读取 | `+0x14`，请求值为 `0x10` |
| `0x3679c4` | `+0x14`，以 `r7+0x1c` 读取 | `+0x18` |
| `0x3b29d0` | `+0x18`，以 `r7+0x20` 读取 | 在本函数内取出并写入 |

这三处帧指针均为入口 SP 减 8；入口 SP 与分配局部空间后的当前 SP 不是同一基址。工具逐一核对加载和转存，不凭相同数字推定同一参数。

在相应公共完成分支，`0x3b31f6` 读取输出指针；若非空，`0x3b3228/0x3b322c` 将选中任务记录 `+0xc` 写到它指向的字段。任务记录数组链接地址 `0x1a539a8`，间距 `0x40`。这比“只知道回调读取该字段”前进一步，但尚未证明所有分支、所有上下文实例和重用时刻均一致。

## 2. 任务令牌来自服务对象，不能直接等同下层句柄

`0x3b29d0` 根据实际任务编号通过 72 项 TBH 分派。编号 15–18 的表目标为 `0x3b2e1e`，相关成功分支执行：

```text
0x3b2e2c → 0x3dd778 → 0x43f320 → 0x4380bc
```

该分支将本地 `+0xa8` 的地址作为输出指针逐层传递。服务成功路径在 `0x4381e8` 调用 `0xa9ce0a`，读服务对象 `+0x90`，再通过两层指针写到上述输出位置。公共记录更新从本地 `+0xa0/+0xa4/+0xa8` 连续加载三个字，`0x3b307e` 的双字存储把第三个字放到任务记录 `+0xc`。

服务字段 `+0x90` 的一处生产方法也已核对：`0xaa0f94` 读取管理对象 `+0xc` 的 u16 计数，增加 1、按 u16 保存，再调用 `0xa9ce10`，计算：

```text
low16(管理计数 + 1) OR (服务对象的 +0x8c 字节 << 16)
```

下层驱动上一轮的句柄也包含低 16 位计数和高位选择信息，但**相似编码不证明计数器、对象编号或句柄身份相同**。本轮没有把服务对象 `+0x8c` 的生产者和实际选择完整连接到捕获模块 `+0x24`。

另须区分：请求值 `0x10` 交给 `0xa02332` 等选择逻辑；TBH 的 0–71 是实际任务编号。尚未完成二者在这次上下文调用中的完整选择条件，不能把请求 `0x10` 直接当成任务编号 16，也不能把所有输出都归于上面的服务分支。

## 3. 更正虚表入口，连接另一类打开与释放

选定模块虚表链接地址仍为 `0xe769dc`。本轮核对：

| 虚表偏移 | 文件偏移 | 已观察行为 |
| --- | --- | --- |
| `+8` | `0x3791dc` | 打开，沿用第十二轮证据 |
| `+0xc` | `0x37936c` | 比较传入配置与模块保存的配置，返回匹配结果 |
| `+0x10` | `0x379444` | 基础释放包装使用的入口 |

**更正第十二轮交接的入口猜测：`0x37936c` 不是关闭函数。** 历史调查记录保留；本轮及滚动交接使用核对后的 `+0x10 → 0x379444`。

配置模式为 1 的打开函数 `0xaaaa78` 同样使用 `0x445168` 选择路由，随后调用 `0x4452d4`，类型参数为 1、发布参数为 1；发布类型字为 2。模式 0 的对应类型字为 1。不能因为共用选择器就省略不同类型的匹配条件。

释放入口先调用 `0x44673c`，相关检查通过后按模块 `+0x148` 的模式值选择：模式 0 到 `0xaaa222`，模式 1 到 `0xaab1e0`；后两者分别以类型参数 0/1 调用 `0x445788`，然后调用 `0x4458d8`。

`0x4458d8` 按路由清除注册表 `0x1a7e578` 的类型字。路由 4 显式清零 `+4/+0xc/+0x14/+0x1c`，没有在这个清除函数内显式清零对应句柄字。类型字清除发生在后续清理调用之前；**不能把整个释放过程当成失败时自动回滚的事务**。

## 4. 引用计数和失败分支的范围

基础包装 `0xa0a0cc` 读取模块 `+0x28`：

- 计数为 1 时，以模块 `+0x24` 的句柄调用虚表 `+0x10`。返回成功字节非零后，将模块句柄置为 `0xffffffff`，再递减计数。
- 这条最后引用分支返回失败时，包装跳过自身的句柄和计数存储；这不证明下层调用没有先清类型字或产生其他副作用。
- 计数不为 1 时走直接递减分支；其中包括数值为零时的无符号回绕。尚未核对所有调用者的先决条件和并发保护，不能宣称完整生命周期安全。

本轮只确认这些静态分支，未执行原固件，也未修改任何检查来放行未知状态。

## 5. 地址更新入口仍不能补齐捕获像素链

已独立核对 `0x173270` 函数边界，其中 `0x173456` 调用 `0xa59652`，端口参数固定为 `0xad`。该函数相关检查成功后进入 `0xa5896c`：首字节非零会再次将 `+0x20/+0x18` 清零，首字节为零的分支才复制参数 `+4/+8`；还存在格式匹配、对齐和范围等检查。

此调用端口与第十二轮的捕获候选端口 `0x5a/0x6e/0x82/0x96` 不同。确认独立更新入口不等于确认捕获格式 3/4 的后续有效地址，不能据此填补有效像素输出或硬件方向结论。
