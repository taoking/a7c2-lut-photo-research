### 同一路由连接配置上下文和通道范围

User3D `0x44615c` 通过此前核对的恒等表，将逻辑路由 0–6 映射到配置上下文 0–6。`0x446346 → 0xa71576` 提交配置，返回 0 时，`0x446360/0x446362` 将原路由交给 `0xaaafac`。

`0xaaafac → 0x446914` 通过七项 TBB 取得通道首尾索引，再逐通道调用 `0xaac326`。表字节和填充 `[0x44692a,0x446932)` 不作代码解码，全部目标核对指令边界。

| 逻辑路由/配置上下文 | 逐一调用的通道（含首尾） |
| --- | --- |
| 0、1、2、3 | 分别为 0、1、2、3 单通道 |
| 4 | 0–3 |
| 5 | 0–1 |
| 6 | 2–3 |

这是同一路由的两种静态映射：七个配置块不是四个通道的一一对应，也没有证明实际运行使用了哪条路由。

### 通道控制字第 28 位的置位/清零构造

`0xaac326` 在本地结构 `+0x68` 写入 1，再以通道为参数调用 `0xaaa0d2`。后者：

1. 从软件缓存 `0x1a7e538[通道]` 取旧控制字；用输入 `+0x68` 的低 1 位替换旧字的第 28 位。
2. 从链接表 `0xe9d550` 取该通道块基址，向其 `+0x1100` 写入构造值，再更新同一软件缓存。
3. 读回寄存器到另一记录位置并执行 DSB，**没有比较读回值**。入口 `0xaaa11e` 读取的第 28 位也来自软件缓存。

因此，保留的是缓存中的其他位，尚未证明缓存与当前硬件一致；写后读回、DSB 或外层返回 0 都不能作为硬件写入成功验证。第 28 位的功能名及极性仍未确认，不直接命名为照片 LUT 使能。

另一构造器 `0xaac34a` 清零 `0x6c` 字节本地结构，将同一 `+0x68` 的 0 交给同一写入器；已定位一处调用 `0xaaad64`，尚未完成其模式/拍摄生命周期。ARM 交互调用的清零入口 `0x516d00` 及后续填充代码单独按 ARM 解码，核对零值参数、字节/字写入与循环边界。

四个通道块基址为 `0xf4000000 + (通道 << 20)`。此前捕获描述第 3 项的端口 `0x5a/0x6e/0x82/0x96` 分别映射到同块 `+0x380`，从而连接到相同静态 MMIO 块。**这不是有效像素传输、同一运行句柄或 MAIN 缓冲身份的证明。**

### 同偏移的 RAM 镜像与同步缺口

所查其他写入 `0xa734d6` 将同样的三组公式写到 `0x25f7078 +0x400/+0x410/+0x414`，这里的基址属于 RAM 镜像，不是前轮配置硬件基址。另一个读取快照 `0xa73c4a` 取得配置基址后，于 `0xa73d52` 从 `+0x400` 读取 32 个字到 `0x25f75f8` 的同偏移区。所查复制前来源/目的寄存器未重设；仍不代表所有别名和被调函数无副作用。这些关系可用于继续找字段说明，尚未给三个寄存器的位赋予业务名称。

User3D 的第 28 位调用位于配置描述提交返回成功之后；所查调用方没有在两者之间显式等待前轮消费端的控制器完成信号。这不能证明配置命令先执行完，也不能反向断言置位一定先发生。完整排队、锁和硬件同步仍是缺口。
