# LUT 链路调查：回调消费者与独立主图 JPEG 入口

日期：2026-10-18。沿[第六轮](LUT链路调查记录-第六轮.md)继续分析同一官方原版 CP 2.01，材料和完整指纹见[首轮记录](LUT链路调查记录.md)。本轮只读，没有执行固件或操作相机。

本轮把描述符提交、消费者及包装函数到 LUT 分发器的间接连接展开，并定位独立的 `MAIN` JPEG 调用段。**LUT/VFX 的输出缓冲与主图 JPEG 输入仍未对应，因此没有完成机内照片 LUT 直出。**

## 1. 事件任务如何消费描述符

第六轮已确认 `0x407f1c` 整理 28 字节描述符并提交。本轮进一步定位：

| 部分 | CP 文件偏移 | 证据 |
| --- | --- | --- |
| 任务对象初始化 | `0xa26fee` 起 | 对象存放入口包装、循环函数、对象自身地址以及队列字段 |
| 对象入口包装 | `0x644a62` | 读取对象 `+8/+0xc` 的函数与调整量，取得 `+0x10` 的对象参数，再间接跳转 |
| 消费循环 | `0x408020` | 从对象 `+0x18` 取得队列字段，接收描述符到栈缓冲 |
| 接收调用 | `0x40804e` | 同一对象字段作为接收 API 参数，接收缓冲为 `sp+4` |
| 间接调用 | `0x408094` | 从描述符取得函数/调整量和两个参数，调用包装函数；随后回到接收位置 |

`VD_Pre` 提交的描述符首项指向 `0x768878`，调整量为零。该包装函数从描述符 `+8` 取出目标，把首个参数转为 `r0`，跳到第六轮确认的 `0x3cf484`。这连接了快照刷新回调的消费者，但未证明接收 API 在错误或取消情况下的完整行为。

本轮没有把循环代码当作任务已启动、队列已送达或固定频率执行的证据。接收 API 返回值与失败路径仍应进一步展开。

## 2. VFX 回调链表的消费者

第六轮已确认 `0xa20c16 → 0xa214e2` 将描述符和参数复制到链表节点。本轮核对生产者和消费者都引用链接地址 `0x1a69b34`，并得到以下连接：

```text
0x3bef8a 提交
  → 0xa20c16 整理参数
  → 0xa214e2 插入链表节点
  → 0x3b74c0 中遍历该链表
  → 0x3b7538 间接调用包装函数 0xa234ac
  → 包装函数从描述符 +8 取目标，转交对象参数
  → 0xa234c2
  → 0xa234d4 调用 LUT 分发器 0x3e076c
```

节点 `+8` 为描述符起点，节点 `+0x1c/+0x20` 为两个参数。原提交处的 `r2 = fp`、`r3 = 0` 在局部窗口内没有再被改写；它们对应消费者传入包装函数的两个参数。包装函数把首个参数作为实际回调的对象。描述符首项是包装函数，`+8` 才是实际回调，不能把两者混为一个指针。

消费者还可调用节点持有对象的虚方法，遍历结束后清空链表。本轮没有将这个虚方法认定为 LUT 缓冲释放，也未证明节点存活时间或跨任务同步。

## 3. 刷新与 VFX 消费位于不同队列

VFX 链表消费者在 `0x3d414e` 被调用。其所属回调入口为 `0x3d40b4`，通过 ADR 引用 `VD_CO S` 日志。这个回调也提交给事件任务，但与 `VD_Pre` 使用不同对象：

| 回调 | 任务对象链接地址 | 对象 `+0x18` 的队列字段 |
| --- | --- | --- |
| `VD_Pre`，含快照复制 | `0x1a6a6c8` | `0x3c` |
| `VD_CO`，调用 VFX 链表消费者 | `0x1a6a708` | `0x45` |

两个对象配置相同的循环函数 `0x408020`。本轮核对初始化字段、实际提交的对象常量以及消费端字段来源，**没有把不同队列解释为已知先后关系**。即使提交语句在同一函数里按顺序出现，也不能证明前一任务完成后后一任务才运行。

因此“快照复制 → LUT 上传 → 图像传输”的完成顺序仍需沿事件标志、就绪回调和等待条件追踪。`VD_CO` 名称也不用于直接推断照片/视频枚举。

## 4. 独立的主图 JPEG 调用段

找到三个明确标签及其调用位置：

| 标签 | CP 调用偏移 | 后续入口 |
| --- | --- | --- |
| `Stage_EncodeJpeg_SCN` | `0x384fca` | `0x385278` |
| `Stage_EncodeJpeg_THM` | `0x38584e` | `0x385278` |
| `Stage_MainEnc` / `EncodeJpegBase MAIN` | `0x385b80` | `0x385278` |

共同函数在 `0x385442` 调用包装函数 `0x376e48`；包装函数在 `0x376e9a` 调用 `0x42673c`，后者引用 `ddl_jpeg_encode` 标签。检查了共同函数到包装调用、包装入口到驱动调用的潜在控制流路径，不能仅凭字符串命中定位。

这里确认的是独立 JPEG 段及 `MAIN` 调用者。共同函数同时服务其他图像，因此命中共同函数或 JPEG API 不足以证明 LUT 作用于主图。**输入地址、宽高、像素格式与 VFX 输出的对应仍然缺失，尚不能称为全分辨率照片像素链。**

## 5. 工具、测试与后续

新增 [trace_lut_schedule.py](trace_lut_schedule.py)，只接受原版 CP 完整指纹。它复核第六轮已有断言，再核对消费者、任务对象、包装函数和独立 JPEG 段；只输出偏移、布局和证据摘要。

新增直接成员指针解析函数，按本轮实际指令形式计算有符号调整量 `ASR #1`，分别处理函数的 Thumb 位与调整量中的虚调用标记。需要虚表、ARM 入口、越界地址或无效位宽时拒绝推导；不猜测运行时节点地址。新增 [test_lut_schedule.py](tests/test_lut_schedule.py) 的 9 项合成测试，覆盖标记区分、有符号极值、映射末端、32 位回绕、类型及错误固件拒绝，没有嵌入 Sony 程序片段。

潜在路径仍使用第六轮的保守结构分析：不求解分支条件，按 ABI 及调用可返回解释。运行、完整照片链和设备命令三个标志保持 false；另明确报告跨队列顺序、LUT 输出到 MAIN 输入、完整尺寸验证都为 false。命令见[研究说明](README.md)，本地报告为忽略目录中的 `research/output/lut-schedule-v3.json`；实际验证结果见 [plan.md](../plan.md)。

下一轮优先处理两个具体缺口：沿 `0x3dfedc` 的 VFX 传输参数与 `0x385278` 的 JPEG 输入结构，对应地址/尺寸/格式；沿 `VD_Pre`、`VD_CO` 之间的事件等待和 LUT 就绪回调，确认消费顺序。之后才能判断静态照片路径需要怎样的独立实验候选。
