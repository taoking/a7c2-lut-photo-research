### 八个后续字段不能自动补齐地址对

`0xaac7c6` 构造步长 `0x44` 的行；`0xaaeafc` 将行 `+0x20` 传给 `0xa59730`，成功分支再调用 `0xa58b50`。与此前格式 3/4 清零的 `+0x20/+0x18` 地址寄存器分开，下表是本轮核对的第二组字段。偏移均为十六进制，构造值不等于已经实机写入的值。

| 行偏移 | 读取宽度 | 端口寄存器偏移 | 所查直接构造 |
| --- | --- | --- | --- |
| `+0x28` | u32 | `+0x28` | 乘加、移位派生；部分分支另写此字段 |
| `+0x20` | u16 | `+0x2c` | 除法/计数派生半字；部分分支另写此字段 |
| `+0x2c` | u32 | `+0x30` | 条件式算术量或 0 |
| `+0x22` | u16 | `+0x34` | 条件式半字量或 0 |
| `+0x30` | u32 | `+0x38` | 公共尾部写 0 |
| `+0x24` | u16 | `+0x3c` | 公共尾部写 0 |
| `+0x34` | u32 | `+0x40` | 公共尾部写 0 |
| `+0x26` | u16 | `+0x44` | 公共尾部写 0 |

独立的行 `+0x18 → 寄存器 +0x24` 来自两个选定标量的 32 位乘积再逻辑右移 3 位；本轮不将它命名为新基址。原候选地址对另经带进位加法、规范化，写行 `+0x10/+0x14`，但格式 3/4 的初始寄存器清零事实仍成立。第二组写入不回写那两个地址寄存器；这不能证明实际传输停止，也不能证明其余字段就是有效像素地址。

还核对 `0xa59526` 所在函数的继续段：`0xa595d8` 会在另一条件下从 `0x1a742b0` 调用同一第二组写入函数。不能把本轮行构造当作唯一写者或覆盖全部初始化效果。

### 四项掩码表和位约束

`0xa59730` 先调用 `0x40e9e0`，后者读取所选端口寄存器 `+0x1c` 的位 18–19，选择文件 `0x40ea08` 起的四项 u32 表：`[7,1,15,0]`。脚本将这 16 字节与代码分离，不反汇编为指令。

第二组输入的四个 u32（相对该输入 `+8/+0xc/+0x10/+0x14`）均要求与掩码按位与为零，才进入直接写入。这里只保留位约束，不据表值推断已验证的像素格式、字节对齐单位或照片尺寸。

### 捕获与 MAIN 之间的实际查询边界

捕获构造调用 `0x381a3a` 和 MAIN 调用 `0x385a00` 都从各自工作对象的 `+0x5afc` 槽取值，再调用 `0xa13bb2`。同偏移槽位并不证明工作实例、运行时刻、槽值或两次响应相同。

`0xa13bb2` 以第三参数 5 调用 `0x409858`。后者构造消息头 `0x2a`、命令 `0x55`，把查询句柄写到请求 `+8`，再调用 `0xae401c`。返回后可见检查包括状态半字 `+2=0`、回复头 `0x802a`、回复命令 `+6=0x55`，以及半字 `+8` 和字 `+0x20` 非零；通过后将回复 `0xd8` 字节复制到调用者输出。

回复 `+0x18` 双字在捕获配置中落到 `+0xf0`；MAIN 另从同样的回复偏移复制到本地 JPEG 参数。现在缺的是**接收端如何按句柄生产回复，以及跨阶段的实际缓冲身份与所有权**；相同查询包装和字段偏移不能替代这段证据。本轮不宣称完整消息路由或运行送达已验证。
