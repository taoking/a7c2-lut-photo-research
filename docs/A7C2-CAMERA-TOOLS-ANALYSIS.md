## 已提供的功能

| 功能 | 源码支持 | 本次能够确认的范围 |
| --- | --- | --- |
| FL2/FL3 | AP/CP 补丁、启动覆盖数据、运行时颜色表和 BK4 持久化 | 有完整功能路径和固定候选检查；本次未实拍比较颜色 |
| 原厂电子快门声 | 接通机内已有声音及菜单路径 | 可以不上传音频，使用机内 KindID 3 样本；不等于改变机械快门动作 |
| 自定义快门声 | MP3/WAV 解码、资源扩展、注册长度和固件重打包 | 限长 2 秒，可选 1–100% 音量；有时长、编码和响度单元测试 |
| 组合安装 | `feature_package_200.py` 组合所选特性 | 支持 FL23、仅音效、两者同时安装；“仅音效”分支会跳过 FL23 颜色写入 |
| 跨平台交互与续跑 | 各平台 UI、按机身记录的工作目录和阶段状态 | 是不同平台的两套实现；不能用一端测试代替另一端实机验证 |

音频实现并非简单把 MP3 放进存储卡。`sound_package_200.py` 经 FFmpeg 转换为 24 kHz 单声道浮点采样，归一化后编码为受限格式：每 31 个 8 位有符号采样前加一个控制字节，形成 32 字节帧。资源长度随输入时长变化，只在末帧补齐。代码随后扩展 CP 分区内 FAT12 的 `SYSSOUND.BIN`，同步两份 FAT、目录项和 AP/启动覆盖模块的注册长度。输入时长、文件大小、占用簇和指令立即数容量均有检查。[音效构建源码](https://github.com/YuuLuo/a7c2-camera-tools/blob/f124d87c26110a82db54775bfa64a0843ff21410/macos/mac_service_readonly/sound_package_200.py)

没有看到提供任意 `.cube` 照片导入、六槽 LUT 拟合、颗粒算法、新 AF 或高规格视频解锁的产品入口。它可以为新增声音功能提供直接研究依据，不能视为本项目任意照片 3D LUT 支线已经打通。

## 安装架构与旧 FL23 工具的区别

源码中的运行链路为：

```text
官方 2.01 DAT + 原厂 2.01 机身
    → 逐机保存 p1 与 Backup.bin / Backup.bak，检查结构与固定属性
    → 离线构建标示版本为 2.00 的修改 DAT，整包解密校验并复制到照片卡
    → 经 USB 服务入口加载临时模块，应用临时 p1 更新门控
    → 暂时调整运行时版本比较，引导用户在机身菜单执行更新
    → 恢复本机原始 p1
    → 选 FL23 时处理运行时颜色表，并检查/按需提交两份 BK4
    → 用户冷启动，进行后续回读及菜单/照片/声音确认
```

1. **目标“2.00”来自官方 2.01 的修改构建。** 构建器核对原始 DAT 的固定 SHA-256，解密修改后重算相关校验，再加密并逐块解密比较。它不是下载旧版官方 2.00 后安装，也不能把菜单上的 2.00 当作具体程序内容身份。[离线构建器](https://github.com/YuuLuo/a7c2-camera-tools/blob/f124d87c26110a82db54775bfa64a0843ff21410/macos/mac_service_readonly/fl23_package_200.py)
2. **DAT 仍依赖相机侧临时门控。** 构建器自己记录 `camera_side_gates_in_DAT: false`；主流程另行修改 p1 并启动受限时间的运行时版本比较窗口。因此，不能把它描述成“任意原厂机身无需前置处理，放卡即可接受修改包”。[p1 控制流程](https://github.com/YuuLuo/a7c2-camera-tools/blob/f124d87c26110a82db54775bfa64a0843ff21410/macos/mac_service_readonly/p1_gate_generic_200.py)
3. **机内模块加载路径不同。** 当前项目旧安装器使用指定 `libJit.so` 临时加载；目标仓库使用 preload 与 DEBUG 子进程触发。其模块检查预期进程及 preload 内容，并设计了删除 preload、输出带校验结果和退出子进程的步骤。虽然触发命令对应 shell/date 路径，受限模块会提前退出；不能据此简单断言正常执行必然修改时钟，也不能忽略加载/清理失败的额外边界。[原生源代码](https://github.com/YuuLuo/a7c2-camera-tools/tree/f124d87c26110a82db54775bfa64a0843ff21410/native/source)
4. **颜色持久化路径不同。** 该仓库从本机 BK4 派生一份固定 8 KiB 颜色属性，先处理 CP 运行时状态，再核对两份 BK4；全部已为目标时避免重复写，混合或未知状态拒绝继续。当前旧 FL23 工具的目标程序、两个 CP 单元和 AP 绑定不与之通用。[属性派生](https://github.com/YuuLuo/a7c2-camera-tools/blob/f124d87c26110a82db54775bfa64a0843ff21410/macos/mac_service_readonly/color_property_200.py)、[持久化处理](https://github.com/YuuLuo/a7c2-camera-tools/blob/f124d87c26110a82db54775bfa64a0843ff21410/macos/mac_service_readonly/commit_bk4_generic_200.py)

本次从清单统计，目标 FL23 包为 AP 6 个窗口、CP 19 个窗口和启动覆盖区域 4 个位置；音效清单另有 AP 8 个窗口、启动覆盖区域 6 个窗口及声音资源改动。它们不同于当前旧安装器的 40 个固定窗口。修改更少或更多都不能直接换算安全性或画质。

先前本地分析所说“旧固定上游没有完成修改 DAT 安装路线”仍适用于当时的代码；**这个新仓库已经给出了另一条具体实现，应该更新能力判断。** 它没有改变旧安装器的验证范围，也不证明旧锁定的文件可以直接替换成新资产。

## 做得较好的保护

- **候选检查有多个层次。** 官方 DAT、部分完整程序/分区、修改窗口、上下文与输出明文均有固定身份或字节检查；复制到卡后按完整包哈希回读。自定义声音候选变化时也有独立 manifest 和输入音频身份。
- **逐机数据参与构建。** p1 片段与原始 checksum 从本机采集派生，原生模板中的相关槽位初始为空；主机重建预期 worker 后核对待执行字节，而非直接分发某台机身的完整数据。
- **写入前后均有证据。** p1 安装/恢复分别组织验证、操作、再验证序列；BK4 核对记录结构、属性和 checksum，并在写入后独立采集。原生写入模块有局部失败恢复尝试。
- **未知写入结果通常不自动重试。** Mac 主流程拒绝从若干 `*_started` 写阶段直接续跑。p1 首次恢复的有限重试也要求日志只到第一个验证步骤，不是通用强制恢复开关。
- **模块来源更便于审计。** `native/` 提供 C 源码、私有头文件生成器、Zig 0.14.1 编译脚本和模板/加载段比对脚本；本轮只审阅这些文件，没有完成源码到二进制的独立复现。[原生构建说明](https://github.com/YuuLuo/a7c2-camera-tools/blob/f124d87c26110a82db54775bfa64a0843ff21410/native/README.md)

## 实质风险与待补证据

| 观察 | 代码依据与限制 | 对使用/复用的影响 |
| --- | --- | --- |
| 修改对象比旧工具更广 | 涉及 p1、运行时版本比较、整包更新、CP RAM 和保存文件；这些动作不是单一原子事务 | 临时门控恢复、固件更新和颜色持久化失败要分别判断；备份不保证无法启动时可恢复 |
| “恢复原始 p1”不等于卸载全部功能 | Mac 的 `restore_only` 调用 p1 恢复，未在此路径还原已装 AP/CP/声音/BK4 | 不能将其叫作完整恢复原厂或通用救砖；作者提到的官方更新后续路线，本轮没有实机验证 |
| 主流程未见跨进程相机独占锁 | 审查 Mac/Windows 入口和锁相关调用，未发现跨进程锁；私有文件权限和阶段记录不能替代互斥 | 复用时应接入当前项目的全局相机锁，防止同时开两个流程或与旧工具并行；本轮没有复现竞态 |
| Mac 仅音效的最终确认较弱 | `a7c2_200_oneclick.py` 在正常 USB 重新出现后记录 `sound_cold_verified`，最后要求用户确认菜单版本和声音 | 该字段不表示自动核对音频内容或完整 AP/CP 哈希；应把人工结果与机器结果分开保存 |
| “只读采集”仍有临时设备改动 | p1 采集通过 Work/tmpfs、preload 和临时模块获取读取能力；它只是不写 p1 块设备 | 不能作为零风险的中性备份命令直接引入；服务认证、临时文件、执行和退出仍需独立审查 |
| 固定基线不覆盖现有改装组合 | 预检查要求官方 2.01 的固定颜色属性、特定 BK4 几何和已识别 p1 | 已装旧 FL23/Custom 的机身不能假定可叠加；当前项目也不能按原厂 2.01 接收该工具的 2.00 结果 |
| 电量与供应链门槛有待加强 | 所审主界面以充足电量提示为主；启动器部分依赖使用版本区间，且有 root/管理员子进程 | 未见同旧工具一样的数值电量入口；这不证明 Sony 自身电量保护已失效。复用应固定环境与验证边界 |
| 公开验证材料有限 | 初始提交附带测试，未见逐机脱敏报告或 CI 配置 | 作者实机报告值得参考，但需要独立验证；本轮的测试也不覆盖 USB、断电或真实刷写 |

Mac `p1_restore_started` 的日志限定续接值得研究，但它使用具体输出行和时间关系判定历史阶段。若改动日志格式、并发运行、回执存储或步骤顺序，必须重新验证；不宜抽象成“任何恢复失败都能续跑”。

当前项目已经推进到原生 Creative Look 拟合的 N1/N2，以及 N3 的程序身份、资源/BK4 和输入清单检查；真实材料、完整事务和机身验证仍缺，参见[总计划](../plan.md)与[当前交接](../research/HANDOFF.md)。这个新仓库有价值，但不会自动补齐这些检查点。

| 可借鉴内容 | 建议处理 | 不能直接推导的结论 |
| --- | --- | --- |
| 电子快门声音资源与注册 | 独立保存固定来源和许可，先做离线音频/资源分析 | 不代表本项目 2.01 或 Custom 布局已有兼容补丁 |
| DAT 解析、明文完整回验 | 作为独立离线研究参考，先以合成输入或合法官方材料验证格式 | 不能顺势将旧安装器改成 p1/整包更新路线 |
| 空模板、本机材料重建和回执 | 可借鉴到 N3 worker 的来源绑定与确定性检查 | 不代替当前程序身份、同机身/捕获新鲜度和完整逆向验证 |
| BK4 双文件与运行时先后关系 | 对照现有 BK4 审计，研究 RAM/保存值/文件一致性 | 两份机内 BK4 不是两份独立介质备份，也不是跨步骤原子提交 |
