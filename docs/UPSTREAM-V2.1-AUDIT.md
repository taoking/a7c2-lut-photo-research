## 3. 两条路线及 M2/M3 的交集

| 项目 | 原生 Creative Look 拟合 | 任意 3D LUT 机内执行 |
| --- | --- | --- |
| 本轮实际发现 | 上游已有解析、拟合、参考预测、设备事务及单机更新记录 | 本地仍为静态控制/缓冲研究 |
| 数据表示 | 5×9×9×3 原生修正，1,215 字节，系数 -64..63 | 目标是较完整地执行输入 CUBE；当前未打通 |
| 输入契约 | Sony ST 编码输入，或有证据的输入空间桥接；选中槽需 ST | 色域、伽马、有效传输及照片使能仍未闭合 |
| 照片证据 | 上游同一台 Windows 机身、既有六槽版本的两次更新 | 本地尚无完整 LUT→MAIN 运行证据 |
| 当前优先级 | N1–N4 交付主线 | M2–M6 研究支线，暂停自动推进 |

交集是同一机型/原版材料，以及外观选择、缓存上传、精确程序身份、设置保留和缓冲寿命等工程问题。两者的数据结构和接入方式不同；不能把原生修正表当作任意 CUBE 的无损执行，也不能用上游照片报告补齐本地 User3D/VFX 到 MAIN 的断点。

现有 M2 的导入/提交关系和 M3 的同配置候选、句柄替换及间接调用边界继续有效。它们既不是完整照片路径证明，也不是原生拟合交付必须先解完的全部前置任务。支线最后入口留在[第二十八轮](../research/LUT链路调查记录-第二十八轮.md)。

## 5. 色彩模型与量化验收

上游已提供 `rendering-model-v1.json`，来源是一组 RAW/ST 场景与原生响应试验，`full_camera_characterization=false`。它不是完整 Sony ISP，也不是本机多场景标定。`native.py` 现有指标是编码 RGB 的平均绝对误差、通道绝对误差 P95 和最大误差，主要在合成随机样本上计算。它们不能直接作为真实照片色彩成绩。依据见[格式/模型说明](https://github.com/QAQLeonard/a7c2-fl23-research/blob/7e54d60b458847f1befa6cfd614fbf004b8b0b90/docs/zh-CN/technical/formats.md)及[验证范围](https://github.com/QAQLeonard/a7c2-fl23-research/blob/7e54d60b458847f1befa6cfd614fbf004b8b0b90/docs/zh-CN/technical/validation.md)。

N2 的完成条件为：

1. 分清普通编码 sRGB、相机 ST 输出和 Log/其他输入；缺少匹配桥接时拒绝拟合。原有 `--lut-space srgb` 声明不能代替 ST 校准。
2. 对同一组输入生成原参考变换和原生表参考预测，保留现有原图/已有输出保护。验证原生表往返、恒等/可表达变换、复杂变换触限和失配拒绝。
3. 报告整体与显式区域掩码下的 RGB MAE/P95、色差、灰阶中性偏移、剪裁比例、系数触限、收敛及样本数；肤色、高光/阴影、高饱和区域没有样本时标为不可用，不用零分代替。
4. 把合成拟合、真实照片参考比较和本机标定验证分开，记录来源/模型哈希、算法版本及随机种子。没有真实数据时保持相机精度未验证。
5. 数据集和具体风格的数值阈值须在查看留出结果前固定；本次 N1 不虚构一个通用合格分数。

N4 才采集本机基准：受控日光型、钨丝型和常用 LED 条件，记录光源、手动曝光/WB、镜头/图像设置及 RAW+JPEG；重复 ST 基线以估计噪声，按场景分训练/留出。分别覆盖灰阶、肤色、绿色、蓝天、高光、阴影，先配准并标记无效/剪裁像素，不通过逐张自动曝光/WB 抵消误差。现有上游展示照片拍摄参数存在变化，不能直接充当这套配对基准。

## 6. 独立迁移与恢复设计

以下是上游适配器的源码支持范围，不是本地真机放行表。代码身份识别不能概括为只认一个永远不变的完整 SHA：可变表区域经过独立检查，程序布局另有规范化哈希，每个实际事务仍绑定完整来源/目标哈希及精确逆向。

| 来源状态 | 上游识别方式/目标 | 恢复应回到哪里 | 当前物理验证边界 |
| --- | --- | --- | --- |
| S0 原厂 2.01 | 固定匹配的完整 AP/CP 对 → 独立自定义槽布局 | 本次事务原厂完整来源 | 上游首次导入未实机；本地未适配 |
| S1 FL2/FL3 2.01 | 固定匹配的完整 FL23 AP/CP 对 → 自定义槽布局 | 本次事务 FL23 完整来源 | 不能套用旧安装器处理新目标 |
| S2 历史六槽 full7-v4 | 审核过的 AP/CP 代码身份及全部表校验 → 所选槽更新 | 本次更新前的六槽状态 | 上游同一 Windows 机身的两次更新报告 |
| S3 独立布局、部分槽已导入 | 完整重建 AP 槽位掩码模板、CP 代码身份与表校验 → 添加/更新所选槽 | 本次事务前的完整程序/资源/设置 | 不冒充已真机覆盖所有掩码组合 |
| 未知或混合状态 | 拒绝，保留现场 | 不拼接其他机身备份，不盲目恢复 | 无通用救援保证 |

`devicejob.py` 分开记录名称、程序、设置和重载；`devicesettings.py` 保护可写 AP `02cf` 组与四个 CP 单元，已知诊断值有单独边界，不能为了通过而忽略其他差异。`0x23` 归还等旧研究结论不替代这些事务保护。

发现两项 N3 必须处理的边界：

- 上游要求独立备份，但代码检查的是两个非嵌套目录和完整文件哈希；这本身不能证明介质独立。新 Mac 流程需记录实际存储介质证据，不能把同盘两个目录称为分盘备份。用户提出的两份独立介质备份用于新 Custom 流程；旧 FL23 工具默认单份规则保持原样。
- Mac USB 尚未实机，Python/本机汇编工具链和 Windows 启动器不能直接照搬。旧 `a7c2-mac restore` 不应接收新 Custom 目标；恢复必须由新事务的精确逆向和已验证边界决定。完整备份也不保证救回无法启动的相机。

上游 v4 为预览缓存增加重传；预览、JPEG、回放、冷启动以及未选外观要分别验证，还需量测帧率、时延、功耗/发热。单台机主的正面报告不能被扩展为这些项目已通过。

## 7. 本地核对结果

- 旧项目 125+39+8 共 172 项离线测试和固定资产检查通过；旧锁/原安装器未改。
- 上游所选 LUT/拟合/设置/模拟调用测试 57 项：55 通过、2 因缺私人完整来源跳过。上游 FL23 离线测试另有 8 项通过。没有把这组选择测试写成“上游全部测试通过”。
- 补齐上游 Python USB 依赖后，其主机测试发现 37 项：28 通过、2 失败、7 Windows 专用跳过。两个失败是启动器测试期待 Windows 环境错误，却在本机先遇到非 Windows 平台拒绝；这是待适配/测试的问题，不靠修改上游断言掩盖。
- 审计环境的 Keystone 0.9.2 在 Python 3.14 下先缺 `distutils`；补充 setuptools 后仍无法加载本机动态库。相关汇编/原生测试未放行，未执行私人来源集成和相机测试。
- 新审计 CLI 的实际包/旧来源检查、同尺寸损坏包拒绝、篡改旧来源拒绝、已有输出保护和 help 均通过；详细命令/结果见[第二十九轮](../research/LUT链路调查记录-第二十九轮.md)。

结论限定为 N1 的方向与源码审计完成。下一轮先实施 N2 的纯离线部分；N3 在独立模拟和代码审阅完成前不进入机身，N4 仍后置并提前提示。
