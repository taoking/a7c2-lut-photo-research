# 持续供电条件下的更新与安全收尾方案

日期：2026-10-22。基线：`6da8b41182521dac53a80428547cdd8486abe8e1`。这是对[全项目回滚评估](ROLLBACK-SAFETY-REVIEW.md)的范围收窄和实现建议，不是新增设备命令或实机验证。本轮只审阅源码、维护文档；没有相机操作。

## 1. 按用户明确的前提重新判断

用户会满电开始、保持供电，提前停止探索并留足恢复余量，优先让相机恢复或保持可用，再充电进入下一轮。两小时续航、半小时操作是说明这个原则的例子，不是本机实际续航、刷写耗时或可自动套用的阈值。本阶段将相机与电脑持续供电作为设计前提，不再把“任意断电后自主救砖”作为首版必须实现的能力。

**结论：这个目标合理，可以推进到“对明确故障有可验证收尾路径”的受控更新系统。当前最优先的缺口是阶段恢复、结果核对和恢复后验证，而不是继续扩大断电救援设计。** 现有代码尚未达到该目标；持续供电不排除USB失联、模块崩溃、存储I/O失败或候选程序本身无法正常启动。

这里的更新指本项目对受限AP/CP、名称资源和设置的修改；官方整体固件升级另按[备份与升级指南](BACKUP-GUIDE.md)处理，不把官方流程当成本项目的恢复执行器。型号、固定2.01完整来源、当前用户版本未确认升级等边界保持。

## 2. 什么状态才算“本轮可以结束”

| 状态 | 要求 | 能否按正常流程结束、充电、下次再试 |
| --- | --- | --- |
| 更新前状态完整保留，未发生持久化修改 | 当前来源已核实、临时操作已核对结束、服务退出正常 | 可以；不凭一个“预检查失败”字样假定上述条件满足 |
| 已回到本轮开始时的已知版本 | 完整源程序/资源、相关RAM及保存态、启动准备、临时状态和服务退出均已核验；冷启动及基本使用通过 | 可以，属于恢复后可用 |
| 新版本完整并已验收 | 完整目标和启动准备核验；真实冷启动、运行状态、菜单、拍摄、回放与USB功能通过 | 可以保留新版本，不因实验时间到点再增加一次恢复写入 |
| 仍能亮屏或当前服务会话仍有响应 | 仅有运行中的现象 | 不足以认定可结束；磁盘与内存可能不一致 |
| 文件/设置处于混合状态，或是否仍在写入不明 | 缺少完整终态与静止证明 | 不能标成可正常重启/可充电收工，不能按时间到点强退 |

将“已准备好进行受控冷启动”与“已冷启动并验证可用”分别记证据。完整哈希只能证明字节符合目标，不能证明目标没有逻辑缺陷。软件更新后的第一次启动仍是实际验收步骤；不能因为操作时一直有电，就提前保证新代码一定启动成功。

“可开机”也不等于“未来官方更新一定成功”。首版可核验正常启动、菜单可达和普通USB；官方更新入口/升级兼容应单列状态与具体版本证据，不为证明菜单存在而触发实际官方升级。

## 3. 将时间限制做成准入规则，而非强制中断器

大部分耗时工作在进入设备会话前完成：拟合、构建/检查正逆向、包与来源核验、准备恢复工具及磁盘空间。真实写入会话内只保留必须依赖当前机身的新鲜检查与有限执行。后续部署产物若需私有保留，仍须核对同一来源、完整摘要和包绑定；不能绕开现有编译/来源契约。

单次安排分为探索预算和收尾预留。每个持久化阶段开始前应判断：

```text
剩余时间 >= 本阶段的保守执行预算
           + 该阶段之后可选收尾路径所需的保守预留
           + 完整读回、正常退出、冷启动和基本验收预算
           + 余量
```

电量也要独立满足相应预留，不能仅按剩余百分比线性折算时间；未建立可靠电量读取时使用刚确认的实际值与保守会话长度，不伪造实时监控。预算值须来自对应版本/机身/操作的实际测量与余量，不能把普通拍摄续航或一次成功耗时当保证上限。

用户示例中的30分钟宜解释为“不再开启新实验/新持久化阶段”的时间点；也可以把30分钟设为希望完成整轮的软目标，但必须提前进入收尾。到点时，若当前步骤尚未完成或结果未知，不得kill主机、拔线、执行第二个worker或强制重启。现有USB等待超时约束主机等待，不证明机内worker已终止；固定原生worker也没有经过验证的主机取消协议。

若下一阶段可能进入一个目前没有恢复路径的状态，即使时间和电量富余也不能据此放行。对于存储永久失效、进程卡死等无法证明有界完成的故障，软件不能保证一定在30分钟内恢复；预算用于提前拒绝冒进，不是恢复成功证明。

## 4. 明确哪些中间状态能设计收尾路径

以下为未来执行器的审阅表，**不是现有工具可直接运行的恢复操作说明**。S指本轮完整源状态，T指本轮完整目标；设置分RAM/保存态。所有动作都要求正确机身、冻结事务、健康且已绑定的会话、worker完成/现场不再变化的可靠证据，以及独立完整读回。日志phase或连续几次读到相同字节不能单独证明worker已结束。

| 经独立核验的现场 | 可以审阅实现的收尾方向 | 当前缺口 |
| --- | --- | --- |
| 程序S、资源S、设置S | 退出临时会话，保留源状态 | 需验证退出/临时状态；不是恢复写入 |
| 程序S、全部资源T、设置S | 在源AP前提下撤销名称资源，核验完整S，再审阅启动收尾 | 固定名称mode2有相应原语；本项目没有真实调度器 |
| 程序T、资源T、设置仍S | 设置确认无需修改；恢复程序至S，再在源AP下恢复资源 | 不能盲调要求目标设置值的逆向函数；需明确“不需要写”的分支 |
| 程序T、资源T、已知部分设置 | 每个属性的RAM/保存值、元数据和保护范围均严格分类后，有限还原设置，再恢复程序/资源 | 有上游分支可审阅借鉴；本项目未集成或实机验证；未知属性不能放行 |
| 程序T、资源T、设置T | 按本轮预定目标完成新版本收尾，或按设置→程序→资源顺序回到S | 还要闭合WBI/重载和恢复后验证，不能只核对文件 |
| 名称资源部分S/部分T，程序S | 若每个文件完整匹配S或T，暂存/备份状态与作业一致且原worker已结束，可审阅有限名称恢复 | 需检查68个文件及残留状态；一个unknown就停止，不能仅看成功计数 |
| 程序窗口部分更新，完整AP/CP不等于S或T | 当前没有可执行的通用收尾方案 | 固定程序mode2要求完整T；不得修改哈希、假造来源或把未知混合字节作为新“原版” |
| 无回执、USB失联、模块可能仍运行 | 保留现场，先解决会话归属和执行是否结束的问题 | 当前失联会话拒绝继续；不能自动重发触发请求、复位USB或运行restore |

程序、资源、设置的真实顺序沿用[settingsplan](../lutphoto/settingsplan.py)72–99行所描述的依赖，而不是简单颠倒正向函数。源/目标都是**本次事务**，不能把连续更新后的L2直接套用L0→L1的逆向。名称不变、程序零窗口或设置已达目标时，只有完整目标比较证明无差异才可省略相应写入；不能凭文件名或界面文字相同判断。

新事务不得把中间阶段当成可正常关机的检查点。收尾过程中同样可能失败，必须保留其自己的意图和独立读回；“正在恢复”不能被当作“已经安全”。

## 5. 持续供电时最重要的三条保护

**先确认结果，再决定下一步。** 写入触发只发送一次。主机没收到回执，不代表相机没执行。未来事故检查必须先建立可靠的同机/同作业/完成状态关联，再读完整程序、资源和设置分类；不得靠旧报告或PID/端口相同直接续写。现有Mac会话拒绝已处于服务模式的设备，重新接入不能通过删掉该保护实现，必须独立审阅身份与执行生命周期。

**把当前会话可用、磁盘完整和下次启动分别验证。** 每步完成只证明该步；在程序/设置/资源一致、需要的启动快照处理已验证、临时模块收尾与服务退出已核对前，不提示关机。早期实验默认回到本轮已知可用基线；验证充分后才允许把已验收的新版本作为下一轮基线。保留新版本仍须通过真实启动和拍摄检查。

**保护恢复所依赖的通道。** 不主动扩大到bootloader、分区表、官方升级器、身份/校准等无关区域。完整指纹和限定窗口继续强制检查。现有恢复仍依赖通信、内核/文件系统及临时模块加载；保持供电不能保证这些永远正常。若模块崩溃或候选影响了该路径，仅靠主机无法保证救回。该类别在验证闭合前必须如实保留，不能因本阶段不测掉电而忽略。

## 6. 已有基础与最小开发优先级

有利基础包括：本项目的完整来源与精确逆向包、程序与名称worker契约、设置作用域保护、全局独占、未知结果停止。固定v2.1的`devicejob.py`还已有名称完成后单独恢复、已知部分设置分类、分开的recover/resume和恢复后验证逻辑。**这些是可审阅的上游实现，不是当前Mac项目已交付能力。** 其重连、报告归属和部分状态规则仍需按本项目约束重新审阅；不直接执行整个上游安装器。

| 优先级 | 要实现的最小交付 | 通过条件 |
| --- | --- | --- |
| 1 | 定义本轮源/目标、终态和有限故障状态；保存不可覆盖的意图/结果 | 最后成功事实、当前观察和失败动作分开；日志/空间/关闭失败后不继续写入 |
| 2 | 只读事故分类与恢复后验证 | 分类器不触发worker写入/设置保存/WBI；活会话和重新接入边界明确；恢复验证覆盖程序、68资源、RAM/保存态、启动与人工使用 |
| 3 | 阶段准入与收尾调度 | 实际时间/电量余量不足时拒绝下一阶段；只从白名单状态执行收尾；无结果不重放；恢复步骤也受同样门槛约束 |
| 4 | 一种来源、一个槽位的正逆执行闭环 | 准备/模块触发/独立读回/退出均绑定本次事务，程序混合态等未覆盖故障持续拒绝 |
| 5 | 测试机实测可用性与有限故障恢复 | 对该冻结版本完成完整正逆循环、冷启动、拍摄/回放、USB重连，记录耗时和电量变化；再决定可接受的单次预算 |

设备端仍先完成D4真实只读首采；持久化写入前核验本人受影响作用域备份和独立介质副本，默认采集单份不变。上面1–3可先做必要代码/接口准备，实际SDK行为和材料绑定需D4证据；不再追加平行模拟层来替代它。

首次建立Custom支持与以后更换风格应分开验收。[slottarget.py](../lutphoto/slottarget.py)已有首次导入与后续表更新的差异处理；已建立且完整匹配的布局可能减少后续程序变更，但不自动代表后续更新已安全。首版固定一种来源/布局和一个槽位，暂不叠加新hook、多槽、其他固件或另一修改工具。完整支持的状态少一些，比增加未经验证的恢复分支更易验收。

## 7. 本阶段怎样认定可靠性有进展

先验证正常闭环，再有针对性地覆盖可检测错误、已知局部回退、结果交付失败和恢复后的重连。故障模拟必须区分主机停止与机内仍执行；同一会话的读取成功不能替代跨启动验证。不得为了测试本评估而在用户主力机上主动制造USB失联、杀死机内进程或破坏程序。

对外可声称的首版目标是：在指定机身/固件/来源及持续供电条件下，正常更新和恢复已实测，并列明哪些失败能够收尾、哪些必须停止审阅。没有覆盖的故障继续列为限制。要承诺“所有不断电故障都能在30分钟内恢复”，还需解决卡死、恢复入口不可达和永久I/O失败；当前没有这种证明，不将它作为首版声明。

**本轮评估调整：暂不要求首版证明任意掉电救砖；要求写入前有真实可用的恢复方案、每个拟支持阶段有收尾条件、每轮最终回到源或经过验收的目标。** 确实未知的故障仍不能伪称已经保障相机可用。
